# i18n — jezyk interfejsu w TimeTrackerze

Dokument dla osoby, ktora dopiero wchodzi w ten kod. Opisuje, jak dziala
warstwa jezykowa, gdzie co lezy i czego **nie** wolno z jezykiem wiazac.

---

## 1. Obslugiwane jezyki

| Kod  | Tag `Intl` | Nazwa    | Rola                     |
| ---- | ---------- | -------- | ------------------------ |
| `pl` | `pl-PL`    | Polski   | jezyk **bazowy**, fallback |
| `de` | `de-DE`    | Deutsch  |                          |
| `en` | `en-GB`    | English  | `en` znaczy **en-GB**    |

Jedno zrodlo prawdy: [`i18n/config.ts`](../i18n/config.ts). Nie ma w repo
drugiej listy `['pl','de','en']` — `Record<AppLocale, …>` wymusza komplet
wpisow, wiec dopisanie jezyka bez uzupelnienia mapowan jest bledem kompilacji.

## 2. Gdzie sa tlumaczenia

```
messages/
  pl/  common.json navigation.json marketing.json auth.json dashboard.json
       calendar.json projects.json clients.json invoices.json reports.json
       settings.json validation.json errors.json seo.json
  de/  … (te same pliki)
  en/  … (te same pliki)
```

Podzial idzie za architektura feature'ow. Klucze sa **semantyczne**:

```jsonc
// DOBRZE
"dashboard.stats.hoursWorked"
"settings.language.title"
"marketing.hero.ctaPrimary"

// ŹLE
"text1", "button5", "headlineBlue"
```

Ladowaniem zajmuje sie [`i18n/messages.ts`](../i18n/messages.ts). Importy sa
**statyczne** (mapa `LOADERS`), a nie `import(\`../messages/${locale}/…\`)` —
dynamiczny literal zmusilby bundler do wciagniecia wszystkich jezykow do
jednego chunka i uzytkownik niemiecki pobieralby takze polski i angielski.

---

## 3. Jak dodac nowy jezyk (np. `fr`)

1. `i18n/config.ts`: dopisz `'fr'` do `APP_LOCALES`.
2. TypeScript pokaze brakujace wpisy w `INTL_LOCALE`, `OG_LOCALE`,
   `LOCALE_LABELS` — uzupelnij je.
3. `i18n/messages.ts`: dodaj blok `fr` do `LOADERS`.
4. `cp -r messages/pl messages/fr` i przetlumacz.
5. Opcjonalnie `COUNTRY_TO_LOCALE`: `FR: 'fr'`, jesli kraj ma jednoznacznie
   wskazywac jezyk.
6. `lib/format/date.ts`: uzupelnij `WEEKDAY_BADGE`, `WEEK_PREFIX`,
   `DATE_SEPARATOR`, `TODAY_LABEL` (TypeScript o tym przypomni).
7. `npm run test` — `__test__/i18n/messages.test.ts` sprawdzi komplet kluczy,
   zgodnosc parametrow ICU i brak pustych wartosci.

Nic wiecej. Routing, sitemapa, `hreflang` i przelacznik jezyka wyprowadzaja sie
z `APP_LOCALES`.

## 4. Negocjacja jezyka

Cala regula stoi w JEDNEJ czystej funkcji:
[`i18n/locale.ts` → `resolveLocale()`](../i18n/locale.ts).

Priorytety, od najmocniejszego:

| # | Zrodlo           | Skad                                        |
| - | ---------------- | ------------------------------------------- |
| 1 | `explicit`       | prefiks jezyka w adresie (`/de/dashboard`)  |
| 2 | `userPreference` | `preferred_locale` z JWT zalogowanego konta |
| 3 | `cookie`         | `NEXT_LOCALE` zapisane przez `LocaleSwitcher` |
| 4 | `geo`            | naglowek `x-vercel-ip-country`              |
| 5 | `header`         | `Accept-Language`                           |
| 6 | `default`        | `pl`                                        |

**Zasada nadrzedna:** swiadomy wybor uzytkownika ZAWSZE wygrywa z automatyczna
detekcja. Geolokalizacja jest wylacznie pierwsza podpowiedzia.

```
DE + brak ciasteczka          → de
DE + ciasteczko pl            → pl        (wybor uzytkownika)
PL + brak ciasteczka          → pl
NL + Accept-Language de-DE    → de
NL + Accept-Language en-GB    → en
NL + Accept-Language fr-FR    → pl        (fr nieobslugiwane)
brak naglowkow                → pl
ciasteczko "<script>"         → pomijane, schodzimy nizej
```

Parsowanie `Accept-Language` robia `negotiator` +
`@formatjs/intl-localematcher` — te same biblioteki, ktorych uzywa `next-intl`
wewnetrznie. Wlasny parser gubilby wagi `q` i dopasowanie `de-AT` → `de`.

Testy: [`__test__/i18n/locale-resolver.test.ts`](../__test__/i18n/locale-resolver.test.ts).

### Geolokalizacja — tylko podpowiedz

Mapa `COUNTRY_TO_LOCALE` jest celowo minimalna (`PL`, `DE`). Reszta swiata
jedzie przez `Accept-Language`, ktory mowi o uzytkowniku wiecej niz adres IP.

Geolokalizacji **nie** uzywamy do niczego innego: nie zmienia waluty, jezyka
faktur, klienta, stawek ani ustawien projektu.

## 5. Ciasteczko i preferencja konta

`NEXT_LOCALE`, `Max-Age` = 1 rok, `SameSite=Lax`.

Zapisuje je **wylacznie** [`i18n/actions.ts` → `setPreferredLocaleAction()`](../i18n/actions.ts),
czyli swiadome klikniecie w `LocaleSwitcher`. Wynik wykrycia po IP **nie**
utrwala sie w przegladarce — middleware podaje go `next-intl` przez ciasteczko
NA ZADANIU, ktorego biblioteka nie odsyla (`syncCookie` widzi wartosc zgodna
i milczy).

Ciasteczko musi dzialac SSR, bo jezyk musi byc znany **przed** renderowaniem
dokumentu. `localStorage` tego nie potrafi — serwer go nie widzi — wiec nie
jest zrodlem prawdy dla jezyka.

Dla zalogowanego uzytkownika ta sama akcja dopisuje `preferred_locale` do
`user_metadata`. To **synchronizacja miedzy urzadzeniami**, nie sciezka
krytyczna:

* gdy w zadaniu nie ma ciasteczka sesji Supabase, akcja w ogole nie dotyka bazy;
* middleware czyta `preferred_locale` z JWT, ktory i tak weryfikuje —
  **zero dodatkowych round-tripow**;
* publiczny landing nie odpytuje Supabase o nic.

## 6. Routing

`localePrefix: 'as-needed'` ([`i18n/routing.ts`](../i18n/routing.ts)):

| pl (bazowy) | de              | en              |
| ----------- | --------------- | --------------- |
| `/`         | `/de`           | `/en`           |
| `/dashboard`| `/de/dashboard` | `/en/dashboard` |
| `/invoices` | `/de/invoices`  | `/en/invoices`  |

Dotychczasowe polskie adresy zostaja bez zmian, wiec ani jeden istniejacy link
ani zakladka uzytkownika nie przestaje dzialac. `/pl/...` przekierowuje na
wersje bez prefiksu — jezyk bazowy ma **jeden** adres, nie dwa.

Drzewo tras: `app/[locale]/{(marketing),(app),auth}`.
`app/layout.tsx` jest celowo **przezroczysty** — prawdziwy root layout stoi
w `app/[locale]/layout.tsx`, bo tylko tam znany jest jezyk potrzebny do
`<html lang>`.

Poza `[locale]` zostaja rzeczy, ktore jezyka nie maja: `app/api`,
`app/sitemap.ts`, `app/robots.ts`, `app/manifest.ts`, `app/icon.svg`.

Testy: [`__test__/i18n/middleware-routing.test.ts`](../__test__/i18n/middleware-routing.test.ts).

## 7. Middleware + Supabase (obszar wysokiego ryzyka)

[`middleware.ts`](../middleware.ts) sklada trzy rzeczy w takiej kolejnosci:

```
1. updateSession(request)   ← tylko dla tras z sesja (panel + auth)
2. resolveLocale({...})     ← negocjacja jezyka
3. handleI18nRouting()      ← rewrite albo redirect od next-intl
4. przepisanie ciasteczek sesji na odpowiedz z punktu 3
```

**Dlaczego sesja jest pierwsza.** `updateSession` odswieza ciasteczka Supabase
takze na obiekcie `request`, wiec rewrite tworzony pozniej przez `next-intl`
niesie juz swieze tokeny do Server Components.

**Dlaczego punkt 4 jest krytyczny.** Warstwa i18n tworzy WLASNA odpowiedz.
Bez przepisania ciasteczek odswiezone tokeny nigdy nie dotra do przegladarki
i uzytkownik zacznie losowo wylatywac z sesji — dokladnie to ostrzezenie stoi
w `lib/supabase/proxy.ts`. Pilnuje tego test regresyjny:
[`__test__/i18n/middleware-session.test.ts`](../__test__/i18n/middleware-session.test.ts).

**Landing nie dotyka Supabase.** `SESSION_PATHNAME` obejmuje tylko
`dashboard | calendar | invoices | clients | projects | settings | auth`
(z prefiksem jezyka i bez). `/`, `/de`, `/en` nie wywoluja `updateSession`.

Matcher wyklucza `/api`, `/_next`, `/_vercel`, `/sw.js`,
`/manifest.webmanifest`, `/robots.txt`, `/sitemap.xml` i wszystko z kropka
w nazwie (obrazki, fonty, favicon).

## 8. Tlumaczenia w Server Component

```tsx
import { getTranslations, setRequestLocale } from 'next-intl/server'

export default async function Page({ params }: { params: Promise<{ locale: string }> }) {
  const { locale } = await params
  setRequestLocale(locale)          // ← bez tego strona wypada ze statycznego renderu

  const t = await getTranslations('dashboard')
  return <h1>{t('meta.title')}</h1>
}
```

## 9. Tlumaczenia w Client Component

```tsx
'use client'
import { useTranslations } from 'next-intl'

export function HoursCard() {
  const t = useTranslations('dashboard')
  return <h2>{t('hours.title')}</h2>
}
```

Komunikaty dostarcza `NextIntlClientProvider` zamontowany w layoucie **grupy
tras**, nie w roocie:

| Grupa            | Przestrzenie wyslane do przegladarki                          |
| ---------------- | ------------------------------------------------------------- |
| `(marketing)`    | `marketing`, `navigation`, `common`                            |
| `(app)`          | `common`, `navigation`, `settings`, `validation`, `errors`, `dashboard`, `calendar`, `projects`, `clients`, `invoices`, `reports` |
| `auth`           | `auth`, `validation`, `errors`                                 |

Landing nie pobiera kluczy faktur, panel nie pobiera kluczy marketingowych,
a strony auth ani jednych, ani drugich. Do tego jedzie **tylko aktywny jezyk**.

### Liczba mnoga i zmienne

Nigdy `count === 1 ? … : …`. Komunikat zalezny od jezyka to komunikat ICU:

```jsonc
// messages/pl/common.json
"days": "{count, plural, one {# dzień} few {# dni} many {# dni} other {# dnia}}"
// messages/de/common.json
"days": "{count, plural, one {# Tag} other {# Tage}}"
```

```tsx
t('days', { count: 5 })   // pl: „5 dni"  de: „5 Tage"  en: „5 days"
```

Test `__test__/i18n/messages.test.ts` pilnuje, ze wszystkie jezyki uzywaja tych
samych zmiennych — brakujacy parametr renderuje sie jako pusta dziura.

## 10. Tlumaczenie Server Actions

Warstwa serwerowa **nie zna jezyka uzytkownika** i nie produkuje zdan. Zwraca
stabilny KOD, a interfejs zamienia go na tekst.

```ts
// features/settings/actions.ts
import { fail, ok, type ActionResult } from '@/lib/errors/action-result'

export async function updateAccountProfileAction(values): Promise<ActionResult> {
  const parsed = accountSettingsSchema.safeParse(values)
  if (!parsed.success) return fail('INVALID_ACCOUNT_SETTINGS')
  …
  if (error) {
    logCause('ACCOUNT_PROFILE_SAVE_FAILED', error)   // szczegoly do logow
    return fail('ACCOUNT_PROFILE_SAVE_FAILED')       // kod do UI
  }
  return ok(undefined)
}
```

```ts
// features/settings/hooks/useAccountSettings.ts
const te = useTranslations('errors')
onError: (error) => {
  const { code, values } = errorCodeOf(error)
  toast.error(te(code, values))
}
```

Wynik jest **zwracany**, nie rzucany: Next.js w produkcji zaciera tresc
wyjatku z Server Action (slusznie — moglaby wyciec sciezka albo zapytanie SQL),
wiec kod bledu przeniesiony w `Error.message` nie dotarlby do przegladarki.

**Surowy blad Supabase nigdy nie trafia do uzytkownika.** Jest po angielsku,
niesie szczegoly implementacyjne i bywa mylacy — zostaje w logach serwera.

Walidacja dziala tak samo: `lib/schemas/auth.schema.ts` zwraca klucze
(`email.required`, `password.tooShort`), a formularz robi
`tv(key, { min: PASSWORD_MIN })`.

## 11. Formatowanie dat

```tsx
// Client Component
const fmt = useFormat()               // '@/lib/format/client'
fmt.date('2026-09-09', 'long')        // pl: 9 września 2026 | de: 9. September 2026 | en: 9 September 2026
fmt.monthTitle('2026-09')             // Wrzesień 2026 | September 2026
fmt.isoWeek('2026-09-09')             // KW 37/2026 | KW 37/2026 | W 37/2026
fmt.dayBadge('2026-09-09').weekday    // ŚR | MI | WE

// Server Component / Server Action
const fmt = await getFormat()         // '@/lib/format/server'

// Modul czysty (bez Reacta) — jezyk wchodzi argumentem
const fmt = createFormat(locale)      // '@/lib/format'
```

Kontrakt sie nie zmienil: wejsciem jest ZAWSZE `IsoDate` (`"YYYY-MM-DD"`),
nigdy `Date`. Zachowane sa wszystkie zabezpieczenia:

* `parseIsoDate()` parsuje na **poludnie UTC** (eliminuje przeskok dnia przy
  dowolnej strefie i przy DST) i jawnie sprawdza zakresy, bo `Date.UTC` cicho
  przewija `2026-02-30` na marzec;
* kazdy formatter daty ma przypieta strefe `Europe/Warsaw`, wiec serwer (UTC)
  i przegladarka renderuja identyczny tekst — zero bledow hydracji.

## 12. Formatowanie pieniedzy

```tsx
fmt.money(123_456, 'EUR')
// pl: 1 234,56 €   de: 1.234,56 €   en: €1,234.56
```

Wejsciem sa **grosze/centy** (int). Funkcja przyjmujaca float nie istnieje
celowo: `580000 * 3` to dokladnie `1740000`, a `5800.00 * 3` to
`17399.999999999998`.

**Zmiana jezyka nie zmienia waluty.** 100 EUR zostaje 100 EUR w kazdym jezyku —
zmienia sie zapis liczby i pozycja symbolu. Pilnuje tego
[`__test__/i18n/formatting.test.ts`](../__test__/i18n/formatting.test.ts).

## 13. Nawigacja swiadoma jezyka

```tsx
import { Link, redirect, usePathname, useRouter } from '@/i18n/navigation'

<Link href="/dashboard" />     // → /dashboard | /de/dashboard | /en/dashboard
redirect({ href: '/auth/login', locale })
```

`usePathname()` z tej warstwy zwraca sciezke **bez** prefiksu jezyka, wiec
dopasowanie aktywnej sekcji (`/de/projects` vs `/projects`) dziala bez if-ow.

**Czego NIE zamieniac** — zostaje `next/link` albo zwykly `<a>`:

* trasy `/api/*` (nie maja wersji jezykowych),
* adresy zewnetrzne, `mailto:`, `tel:`,
* pliki i pobierania z `/public`,
* kotwice w obrebie strony (`#product`) — prefiks doklada `Link` trasy
  nadrzednej, nie sam hash.

## 14. SEO i hreflang

[`lib/seo/site.ts`](../lib/seo/site.ts) daje `localizedUrl()` i
`alternateLanguages()`; [`lib/seo/metadata.ts`](../lib/seo/metadata.ts) sklada
z nich `Metadata`.

Kazda publiczna wersja jezykowa ma:

* wlasny `canonical` wskazujacy **na siebie** (`/de` → `/de`, nigdy `/de` → `/`),
* komplet `hreflang`: `pl`, `de`, `en` + `x-default` (jezyk bazowy),
* `og:locale` (`pl_PL` / `de_DE` / `en_GB`) i `og:locale:alternate`,
* lokalizowany `title`, `description`, OpenGraph i JSON-LD,
* poprawny `<html lang>`.

Sitemapa (`app/sitemap.ts`) publikuje wszystkie trzy wersje landingu, kazda
z pelnym blokiem `alternates`. Trasy prywatne (panel, auth) sa `noindex`,
wyciete w `robots.ts` — takze z prefiksem jezyka (`/de/dashboard/`) — i nie
trafiaja do sitemapy. Strony `noindex` **nie** dostaja `hreflang`: to sygnal
sprzeczny.

Testy: [`__test__/i18n/seo.test.ts`](../__test__/i18n/seo.test.ts).

## 15. Czego NIE wiazac z jezykiem UI

To najwazniejsza sekcja tego dokumentu. Jezyk interfejsu to **jedna** z wielu
niezaleznych osi konfiguracji.

| Rzecz                   | Zrodlo                                   | Czy idzie za jezykiem UI? |
| ----------------------- | ---------------------------------------- | ------------------------- |
| `client.locale`         | `features/clients` (dana klienta)        | **NIE**                   |
| Waluta faktury          | klient / builder faktur                  | **NIE**                   |
| Strefa czasowa          | `lib/format/intl.ts` (`Europe/Warsaw`)   | **NIE**                   |
| Jezyk faktury dla klienta | osobny problem domenowy                | **NIE**                   |
| Stawki, budzety, dane projektu | baza                              | **NIE**                   |
| Nazwy klientow/projektow, numery faktur, notatki | dane uzytkownika | **NIE** (nigdy nie tlumaczymy) |

Poprawna, codzienna konfiguracja wyglada tak:

```
UI = pl
klient = Ignor Bau (DE), client.locale = de-DE
waluta faktury = EUR
strefa konta = Europe/Berlin
```

Przelacznik jezyka **nie rusza** zadnej z tych wartosci. `LocaleSwitcher`
zmienia wylacznie jezyk interfejsu; mowi o tym wprost sekcja
`settings.language.description` w ustawieniach konta.

Dlaczego strefa nie idzie za jezykiem: zwiazanie ich przesuwaloby uzytkownikowi
**biznesowa interpretacje dat** przy samej zmianie prezentacji. Dzien pracy
zapisany 1 wrzesnia ma zostac 1 wrzesnia niezaleznie od tego, w jakim jezyku
patrzy na niego wlasciciel konta.

## 16. E-mail i powiadomienia

`renderWeeklySummaryEmail(supabase, userId, locale)` przyjmuje jezyk
**argumentem**, nie czyta go z kontekstu zadania. Powod: ten sam kod odpala
cron sobotni, w ktorym nie ma zadnego requestu uzytkownika.

* cron (`app/api/cron/weekly-summary/route.ts`) czyta `preferred_locale`
  wlasciciela przez Auth Admin API,
* przycisk „Wyslij teraz" w ustawieniach podaje jezyk biezacego interfejsu —
  klikajacy JEST wlascicielem konta.

**Jezyk wiadomosci dla klienta to osobny problem domenowy** i nie jest tu
modelowany — patrz „Pozostaje do zrobienia".

## 18. Pozostaje do zrobienia

Migracja objela infrastrukture, landing, nawigacje, auth, ustawienia i warstwe
formatowania. Ekrany feature'ow (`features/dashboard`, `calendar`, `clients`,
`invoices`, `projects`, `reports`, `trips`, `work-automation`) maja jeszcze
copy zaszyte po polsku — okolo 570 stringow.

Zasady migracji tych ekranow:

1. Klucze ida do `messages/<locale>/<feature>.json` (pliki juz istnieja).
2. Liczebniki zamieniamy na ICU `{count, plural, …}` — pomocnik
   `fmt.count(count, [forms])` jest oznaczony `@deprecated` wlasnie dlatego
   i ma zniknac razem z ostatnim ekranem.
3. Bledy Server Actions zamieniamy na `ActionResult` + kod z `errors.json`
   (wzor: `features/settings/actions.ts`).
4. `aria-label`, `placeholder` i teksty `sr-only` traktujemy tak samo jak
   widoczne copy — jezykowa salatka ukryta przed wzrokiem jest gorsza,
   nie lepsza.

Poza migracja zostaja **swiadomie**:

* nazwy wlasne i dane uzytkownika (klienci, projekty, numery faktur, notatki) —
  to nie jest copy interfejsu;
* `public/sw.js` — powiadomienia push nie maja jeszcze w payloadzie jezyka
  odbiorcy; poprawka wymaga zmiany kontraktu Edge Function, ktora te
  powiadomienia wysyla;
* jezyk wiadomosci wysylanych do KLIENTA (nie do wlasciciela konta) — osobny
  problem domenowy, wymaga pola przy kliencie, nie przy koncie.
